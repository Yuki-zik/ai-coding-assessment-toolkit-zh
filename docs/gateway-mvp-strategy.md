在 agent 项目考试里，gateway 形态的题目很常见。这份指南的目标是把它们压小。

## 这些术语怎么对应

- `Proxy`：一个很薄的转发层，在保留大部分上游行为的同时，只施加少量请求规则。
- `Gateway`：位于一个或多个模型、工具或服务前面的稳定内部 API。
- `Aggregator`：一种 gateway 风格服务，负责分发到多个来源、合并结果并返回一个响应。
- `BFF`：面向客户端的整形层，把后端或 gateway 的响应适配成特定 UI 或消费者所需的形状。

它们在考试里高度重叠。除非题目明确需要更专门的能力，否则应把它们当作同一类问题处理。

## 2 小时的默认最佳形态

建议目标是：

- 一个入口 endpoint 或 handler
- 一个校验层
- 一个认证或 allowlist 规则
- 一个上游适配器，或者最多两个用于聚合的小适配器
- 一个规范化后的响应结构
- 一个错误格式
- README 中的一节 tradeoff 说明

继承自 ECC 的偏好：

- 保持行动空间显式
- 保持输出结构确定
- 通过减少集成来缩小攻击面
- 优先使用直接适配器，不要过早引入通用路由框架

如果题目含糊，先按 gateway 或 proxy 形态开始。只有当题目明确依赖时，再加入 aggregation 或 BFF 逻辑。

## 推荐的默认技术路线

- 如果考试仓库里已经有现成技术栈，就沿用它
- 优先单进程服务
- 优先内置 HTTP 客户端，或者最小的现有依赖
- 适配器保持为普通函数
- 除非题目要求，否则不要持久化任何内容
- 配置保持显式且精简
- 在边界使用安全的查询或请求模式
- 如果必须的 secret 或上游配置缺失，直接 fail fast

## 各变体的最小交付

### Proxy

- 校验 headers 和 body
- 转发到一个上游
- 用最小化规范化返回上游数据

### Gateway

- 接收一个稳定的内部请求
- 路由到一个上游模型或工具服务
- 规范化响应结构

### Aggregator

- 调用 2-3 个来源
- 规范化结果
- 合并、去重或排序
- 返回来源元数据

### BFF

- 接收一个客户端专属请求
- 调用一个后端或 gateway 路径
- 组织成适合 UI 的响应

## 常见过度设计陷阱

- 动态路由 DSL
- 插件系统
- 复杂的重试和熔断栈
- 在同一个 MVP 里同时加入流式、缓存和聚合
- 通用 SDK 生成
- 管理界面和运维看板
- 宽泛的多上游策略引擎
- contract 中看不见的隐式认证行为

## 最小测试集

只选能证明闭环真实存在的测试：

1. 主成功路径请求返回规范化后的结构
2. 无效输入或不允许的路由失败且失败方式清晰
3. 上游失败返回预期的错误结构

只有当聚合或 BFF 整形是核心价值时，才额外加一个测试。

## README 的 tradeoff 说法

可以直接写成这样：

- “这个 MVP 只支持一个上游路由和一个稳定的规范化响应。”
- “为了压缩考试范围，缓存、重试、流式、多租户策略管理都被有意排除。”
- “如果再多一些时间，下一优先级会是适配器加固和更广的路由覆盖。”

## 安全边界说明

继承自 ECC 的安全材料，但保持最小化：

- 在调用上游之前，先校验 headers、路由参数和 body
- 永远不要硬编码上游 key 或 token
- 不要把上游错误细节暴露给客户端
- 如果 gateway 行为受文档或远程内容影响，应把它们视为不可信输入
