# 2 小时 MVP 范围

## 来源线索

主要继承来源：

- `legacy/ecc-source/agents/planner.md`
- `legacy/ecc-source/commands/plan.md`
- `legacy/ecc-source/rules/common/development-workflow.md`
- `legacy/ecc-source/skills/search-first/SKILL.md`
- `legacy/ecc-source/docs/token-optimization.md`
- `legacy/ecc-source/skills/strategic-compact/SKILL.md`

继承的方法：

- 在动代码之前先复述需求
- 在提出修改前先分析现有结构
- 在编写自定义代码前先搜索可复用内容
- 把工作拆成带成功标准和风险的阶段
- 在阶段边界压缩上下文，而不是在实现中途压缩

## 何时使用

在写代码之前、刚读完题目后使用。

用它来：
- 把任务压缩成 2 小时可交付内容
- 识别应该先构建的唯一主循环
- 拒绝那些诱人但不必要的特性

## 预期输出

- 一段话的题目摘要
- 选定的成功标准
- 明确的 MVP 范围
- 明确的非目标
- 一个小的目标文件树
- 余下会话的大致时间切分

## 流程

1. 用平实语言复述题目。
2. 识别成功标准、假设和约束。
3. 在发明新代码之前，先在仓库和技术栈里搜索可复用模式。
4. 只选一条主路径。
5. 除非题目真的要求，否则把其他内容都变成显式非目标。
6. 勾勒出能支撑主路径的最小文件树。
7. 在写实现代码之前，预留测试和 README 的时间。

## 复用决策

使用压缩版 search-first 决策矩阵：

- `Adopt`：当仓库或技术栈里已经有很接近的实现时。
- `Extend`：当现有模式已经覆盖大部分需求时。
- `Build`：只有在复用比小规模自定义路径更耗时时才选择。

在考试里，常见错误是重建仓库里已经暗示过的基础设施。

## 范围问题

- 哪一个用户或系统动作必须工作？
- 哪些内容可以安全地硬编码、stub 掉或省略？
- 哪些基础设施对 2 小时考试并不必要？
- 哪些边界情况可以只承认存在，而不真正实现？

## 不要做什么

- 不要设计平台
- 不要一上来就从抽象或扩展点开始
- 不要承诺后台任务、管理面板、计费或丰富可观测性
- 不要把非目标藏起来不写
- 不要让搜索或规划膨胀成研究项目
