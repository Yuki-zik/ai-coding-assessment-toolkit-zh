# 最小测试门禁

继承的方法：

- 即使在时间压力下，也要保留 RED -> GREEN -> REFACTOR 的思路
- 从用户旅程和稳定行为出发，而不是实现细节
- 尽可能在实现前定义证明目标
- 对已复现的 bug，先写回归测试再修复
- 用最小检查集证明就绪状态
- 把仍然存在的风险写出来，不要假装覆盖已经完整

## 何时使用

在核心路径已经实现、但还没最终交付之前使用。
如果还没开始实现，也可以先短暂使用它来定义最小证明目标，然后等主路径存在后再回来。

## 预期输出

- 一个很小的测试计划
- 一行版验证标准或验收目标
- 1-3 个能证明 MVP 可用的测试
- 一条关于有意未测试内容的简短说明

## 默认测试选择

只选信号最高的用例：

1. 主成功路径
2. 一个关键校验或失败路径
3. 如果确实能带来额外价值，则加入一个 archetype 专属检查

示例：
- gateway/proxy：有效路由、无效请求、上游失败规范化
- 工具类 agent：工具选择、无效工具参数
- 检索：命中结果、空结果或无匹配响应
- workflow：成功步骤序列、提前失败汇报

## 测试流程

1. 在实现前写下你必须证明的用户旅程或系统旅程。
2. 优先选择能暴露缺失行为的最小失败测试。
3. 如果是修 bug，先用回归测试复现 bug。
4. 只实现或调整足以通过该测试的代码。
5. 每次修复后重跑最小且有意义的检查。
6. 一旦主循环被可信地证明，就停止。

## 先验证

在写代码前，先定义以下任一项：

- 最小自动化验收测试
- 针对已知 bug 的最小回归测试
- 如果技术栈或时间盒阻碍自动化，则采用最小人工验证方法

如果没法先自动化，也要写清楚你将采用的准确证明方式。不要在没有测试目标的情况下直接开始实现。

## 汇报格式

- 选择了哪些测试：
- 验证标准：
- 为什么这些测试重要：
- 还有什么是有意未测试的：

## 测试标准

- 让测试保持小
- 断言稳定行为，而不是实现琐碎细节
- 对真实观测到的 bug，优先使用能防回归的测试
- 一旦主循环被可信证明，就停止

## 不要做什么

- 不要追逐覆盖率数字
- 除非题目依赖 UI 行为，否则不要搭建完整浏览器测试套件
- 不要加那些只是重复 contract、却不增加信心的测试
- 不要在最后 20 分钟把一个可工作的 MVP 改造成完整测试金字塔
